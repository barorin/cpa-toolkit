# 基準ウォッチ

ASBJ・JICPA・金融庁等の新着公表物を収集し、業務への影響つきで要約するスキル。定期実行(週次など)にも対応する。

## モデル振り分け

| 工程            | 実行者                          | 理由           |
| --------------- | ------------------------------- | -------------- |
| ①収集           | **researcher(低コストモデル)**  | 検索・巡回作業 |
| ②影響分析・選別 | メイン(高推論モデル)            | 専門的判断     |
| ③要約整形       | メイン(短ければ)/ report-writer | 分量次第       |

## 手順

### ⓪ 実行ログの確認(メイン)

収集前に必ず実行ログ `${CLAUDE_PLUGIN_DATA}/standards-watch/watch-log.json`(環境変数未定義なら `~/.claude/cpa-toolkit-data/standards-watch/watch-log.json`)を読む。構造: `{"last_run": "YYYY-MM-DD", "reported": [{"date": "...", "source": "...", "title": "...", "url": "..."}]}`。対象期間は「前回実行日〜今日」とし(ログがなければ利用者に確認、既定は過去2週間)、収集結果からログの reported に載っている項目を除外して**差分だけを報告する**。報告後、今回の報告項目を reported に追記し last_run を更新して保存する(reported は直近200件程度でローテーション)。

### ① 収集(researcher に委譲)

上記で決めた対象期間を指定し、以下の巡回を指示する:

- ASBJ/FASF: 新規の会計基準・適用指針・実務対応報告、公開草案、審議状況
- JICPA: 監査基準報告書・実務指針・研究文書等の公表物、会長声明
- 金融庁: 監査基準の改訂、企業会計審議会の動き、開示府令の改正、令和年度有価証券報告書レビューの着眼点
- IFRS財団(利用者がIFRS案件を持つ場合): 新基準・改訂・アジェンダ決定
- 各項目に「公表日・種類(最終基準/公開草案/その他)・適用時期・コメント期限・URL」を付す

### ② 影響分析(メインで実施)

収集結果を選別し、各項目に「何が変わるか(2〜3文)」「影響を受ける会社・取引の類型」「実務対応の要否と時期」を付す。重要度(高: 対応必須/中: 把握しておくべき/低: 参考)で並べ、該当が少ない週は「特筆事項なし」と簡潔に報告する。水増ししない。

### ③ 納品

通常は会話内で簡潔に報告する。月次まとめ等の文書化を求められた場合のみ report-writer に整形させる。

## 定期実行の設定

利用者が「毎週届けてほしい」等を求めた場合、スケジュールされたタスク(週次、例: 月曜朝)を作成する。タスクのプロンプトは自己完結にすること: 「cpa-toolkit の standards-watch スキルを使い、過去1週間の会計・監査基準の新着を収集・分析して報告する。特筆事項がなければその旨を一行で。」設定・解除は利用者の指示に従う。

## 注意

- 一次情報(公式サイト)ベースで報告し、解説記事のみを根拠にしない。すべての項目にURLを付す。
- 適用時期(早期適用の可否を含む)は原文で確認し、不明確な場合は「要原文確認」と付す。

## 共通運用ルール

- **設定ファイル**: 作業開始前に `${CLAUDE_PLUGIN_DATA}/config.json`(環境変数未定義なら `~/.claude/cpa-toolkit-data/config.json`)を読む。設定済みの項目(適用基準の既定、重要性方針、様式、閾値、想定読者等)は確認質問を省略する。恒常的に使えそうな新しい設定を確認したら、利用者の同意を得て設定ファイルに保存する(初回セットアップは cpa-setup スキル)。
- **委譲の例外**: 対象が小さい場合(目安: データ数百件以下、文書数ページ、単一の軽い論点)は、サブエージェント委譲のオーバーヘッドの方が大きいため、メインで直接実施してよい。ただし品質工程(最終レビュー・引用突合)は省略しない。
- **Gotchas を育てる**: このスキルの利用中に新しい失敗・つまずきがあったら、下の Gotchas に追記する(CLI では直接編集、Cowork ではチャットで改訂を依頼するよう利用者に一言添える)。

## Gotchas(実際に踏んだ罠を追記して育てる)

- 公開草案と最終基準を混同して「基準化された」と報告しない。種類(最終/草案/審議中)を必ず区別する。
- 実行ログとの照合を怠ると既報告項目を再報告してしまう。⓪の工程を飛ばさない。
- 適用時期は「原則適用」と「早期適用」を分けて記載する。
