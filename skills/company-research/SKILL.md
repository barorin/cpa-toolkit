# 企業調査とレポート作成

対象企業の概要・事業・商流・会計論点・不正リスクを調査し、レポートを出力するスキル。

**想定読者の前提**: 成果物の読者は会計士だが、対象企業の業種の商習慣は知らない。業界用語も商流の常識も共有していない。レポートを読んだ翌日に経営者インタビューができる状態を目標にする。この前提が、以下の全工程(特に②の収集項目と④の平易化ルール)を規定する。

## モデル振り分け(このスキルの核心)

| 工程                        | 実行者                                         | 理由                       |
| --------------------------- | ---------------------------------------------- | -------------------------- |
| ①スコープ確認・調査設計     | メイン(高推論モデル)                           | 判断を要する               |
| ②情報収集                   | **researcher エージェント(低コストモデル)**    | 検索量が多く推論難度が低い |
| ③会計論点・不正リスクの分析 | メイン(高推論モデル)                           | 高度な専門的推論           |
| ④論点の絞り込みと構成設計   | メイン(高推論モデル)                           | **何を書かないかの判断**   |
| ⑤レポート整形               | **report-writer エージェント(低コストモデル)** | 生成量が多く判断不要       |
| ⑥最終レビュー               | メイン(高推論モデル)                           | 品質担保                   |

④を独立させているのは、**重要な論点は会社ごとに違うため**である。固定の章立てを機械的に埋めた報告書は、重要でない論点に紙面を与えて重要な論点を薄める。何を独立章にし、何を1行に落とし、何を書かないかは高推論モデルの判断であり、委譲しない。report-writer には確定した章立てを渡し、構成の判断はさせない。

## 手順

### ① スコープ確認(メイン)

利用者に確認する(不在時は標準スコープで進め、冒頭に前提を明記): 調査目的(監査受嘱判断/継続監査のリスク評価/取引先調査等)、想定読者、レポート形式(docx/HTML/markdown)、深掘りしたい領域。

### ② 情報収集(researcher に委譲)

Agent ツールで researcher を起動し、以下の調査項目リストと「結果はファイルに保存しパスを返す」指示を渡す:

- 会社概要(商号、所在地、設立、資本金、代表者、沿革、グループ構成)
- 事業内容と商流(製品・サービス、主要顧客・仕入先、ビジネスモデル、収益構造)
- **商流の実務**(取引の開始から代金決済までのステップ、各ステップの当事者・現物・代金・書類、会社が使う取引区分の呼称とその定義、価格の決定者、在庫リスクと回収責任の所在)
- **業界用語と商習慣**(会社の開示や業界記事に出てくる専門用語を、業界外の人向けの日常語で説明できるだけの情報。商習慣の「なぜそうなっているか」を含む)
- 業績(直近3期の売上・利益・財政状態。上場企業はEDINET/決算短信から)
- **開示原文**(重要な会計方針・収益認識の注記・重要な会計上の見積り・事業等のリスクは、要約せず**原文のまま**引用可能な形で保存させる。レポートで原文引用するため)
- 販売実績・取扱実績など、会計上の売上高と流通総額を分けて開示している数値
- ガバナンス(株主構成、役員、監査人、監査人の異動)
- ネガティブ情報(不祥事、訴訟、行政処分、内部統制報告、継続企業の前提、監査意見)
- 業界環境(市場動向、競合、業界特有の会計慣行)
- 許認可・業法(その業種の営業に必要な許認可、輸出入・資金・個人情報等の規制)

### ③ 分析(メインで実施 — 委譲しない)

収集結果を読み、以下を専門的に分析する。**商流の分解を最初に行う**(会計論点も不正リスクも商流から導かれるため)。

**(a) 商流の分解 — 会社の呼称ではなく判定軸で分類する**

会社が使う取引区分の呼称(「◯◯販売」「◯◯サービス」)をそのまま分類名にしない。契約ごとに次の4問で分類し直し、会社の呼称との対応表を作る。呼称と会計上の分類がずれていること自体が論点になる。

1. 引渡し前に会社が対象物の支配(所有権)を取得したか
2. 価格を会社が決定しているか
3. 滞留・毀損・値下がりの損失を会社が被るか
4. 買い手が支払わないとき会社が損をするか

分類の最小単位(1件／1個体／1契約)と、それを識別する一意のキーを特定する。さらに、**1件の取引を代表例として金額入りで追い**、分類が変わると売上高が何倍変わるかを実額で示せるようにする(レポート第4章の中核になる)。

**(b) 会計論点**: 商流から導かれる論点(収益認識の5ステップ上の論点、本人/代理人、履行義務の充足時点とカットオフ、減損兆候、棚卸資産の評価、引当金、税効果、関連当事者取引等)。各論点に適用基準を紐付ける。会社の会計方針の**原文**を読み、文言と実際の処理・表示が整合しているかを検討する。

**(c) 不正リスク**: 不正の3要素(動機・プレッシャー/機会/姿勢・正当化)の枠組みで識別し、監基報240が求める収益認識の不正リスクの推定に言及する。経営者による内部統制の無効化リスクを常に含める。組織規模と事業規模のギャップから、職務分掌が実態として成立しない領域を特定する。

分析の各項目に、根拠となった収集事実(出典付き)を紐付ける。事実・推定・要確認を区別して記録する。

### ④ 論点の絞り込みと構成設計(メインで実施 — 委譲しない)

`assets/report-template.md` の第2節に従い、**この会社に固有の章立てをその場で設計する**。定型の章立てを流用しない。

1. ③で洗い出した論点を、5つの物差し(金額的重要性／見積りの不確実性／不正リスクとの結合／情報の非対称性／**会社固有性**)で順位づける。会社固有性を最も重く見る。どの会社にも当てはまる一般論はこの報告書の価値ではない。
2. **上位3〜5論点を独立章に昇格**させる。章タイトルは一般名詞(「棚卸資産」)ではなく、その会社で何が問題なのかを名指しする(「総資産の49%を占める中古機械を、1台ずつどう評価するか」)。
3. 残りは既存章の一節、または一覧表の1行に落とす。該当がない論点は**「該当なし」と明記**する(黙って省略すると、検討漏れと区別できない)。
4. 最重要論点に本文の6割前後を配分する。会社概要が最重要論点より長い構成は失敗である。
5. 書かない判断をした論点は、理由とともに「調査限界」に残す。

不変の骨格は5要素のみ(表紙＋結論／エグゼクティブ・サマリー／会社概要・経営体制／**事業と商流**／出典・調査限界)。それ以外の章はすべて選択である。商流だけは論点の絞り込みで削らない(会計論点も不正リスクもそこから導かれるため)。

成果物は**確定した章立て(章タイトル・順序・各章で使う部品・分量配分)**であり、これを次工程に渡す。

### ⑤ レポート整形(report-writer に委譲)

以下の引き渡し資料を作成してから Agent ツールで report-writer を起動する:

```
【引き渡し資料】
- 想定読者(=対象業種を知らない会計士) / 文書形式 / 分量目安
- 確定した章立て(④の成果物): 章タイトル・順序・各章で使う部品番号・分量配分
  ※ report-writer は構成を変更しない。章の追加・削除・並べ替えをさせない
- 設計ガイド: 本スキルの assets/report-template.md
  第3節の部品カタログの「型」と「規律」に従って各章を組む
  第4節(商流の書き方)と第5節(納品前チェック)は全文適用する
  (configに事務所様式が登録されていればそちらを優先)
- 調査結果ファイルのパス(researcher の出力)
- 商流の分解結果: 判定軸による分類、会社の呼称との対応、最小単位と識別キー、
  1件の取引の代表例(実額)
- 分析結果: 会計論点(結論・根拠・基準の出典)、不正リスク(要因・シナリオ)
- 引用用の開示原文(会計方針、収益認識の注記、事業等のリスク)。要約せず原文で引くこと
- 「情報が無い箇所は【要確認】でマークし創作しない」
```

### ⑥ 最終レビュー(メイン)

report-writer の成果物を読み、`assets/report-template.md` 第5節の納品前チェック(構成／内容／平易性)を通す。特に次を確認する。

- **構成の整合**:結論ボックスの3〜5点、独立章に昇格させた論点、リスクマトリクスの「最重要」が三者で一致しているか。ずれていればどれかが間違っている
- **分析結果との整合**、**【要確認】箇所の処理**(本文の【要確認】がインタビュー質問集とPBCリストに対応しているか)
- **平易性**:業種を知らない読者になったつもりで商流の章を読み、経営者への質問を自分で作れるか

基準の引用が含まれる場合は standards-checker エージェントに原文突合を委譲する。修正が必要ならメインで直接修正してから納品する。重要案件では reviewer エージェント(高推論モデル)による独立レビューを追加する。

## 注意

- 風説の流布につながる断定を避け、ネガティブ情報は出典と公表日を必ず付す。
- 非上場企業は公開情報が限られるため、確認できた範囲と情報の限界をレポートに明記する。
- 記載は【事実】【推定】【要確認】の確証区分で区別する。推定は根拠(金額の整合、業界慣行等)を必ず添える。
- 各表・各主張の直下に出典行を置く。当方で計算した数値は「当方計算」と明記する。

## 共通運用ルール

- **設定ファイル**: 作業開始前に `${CLAUDE_PLUGIN_DATA}/config.json`(環境変数未定義なら `~/.claude/cpa-toolkit-data/config.json`)を読む。設定済みの項目(適用基準の既定、重要性方針、様式、閾値、想定読者等)は確認質問を省略する。恒常的に使えそうな新しい設定を確認したら、利用者の同意を得て設定ファイルに保存する(初回セットアップは cpa-setup スキル)。
- **委譲の例外**: 対象が小さい場合(目安: データ数百件以下、文書数ページ、単一の軽い論点)は、サブエージェント委譲のオーバーヘッドの方が大きいため、メインで直接実施してよい。ただし品質工程(最終レビュー・引用突合)は省略しない。
- **Gotchas を育てる**: このスキルの利用中に新しい失敗・つまずきがあったら、下の Gotchas に追記する(CLI では直接編集、Cowork ではチャットで改訂を依頼するよう利用者に一言添える)。

## Gotchas(実際に踏んだ罠を追記して育てる)

- **同名・類似名企業の混同が最頻の事故。** 法人番号・所在地・代表者名で対象を同定してから収集する。researcher への指示に同定情報を必ず含める。
- 役員・株主・監査人は異動が多い。「〇年〇月時点」を付けない記載を成果物に残さない。
- 親会社・グループ会社の情報が対象会社の情報として混入しやすい(特に採用サイト・ニュース)。どの法人の情報かを都度確認する。
- ネガティブ情報が「見つからない」ことは「存在しない」ことではない。検索した旨と検索語を記録し、断定を避ける。
- **定型の章立てを埋めにいくと報告書が死ぬ。** 重要でない論点に紙面を与えた分だけ、重要な論点が薄まる。章立ては毎回④で設計し直す。前回の案件の構成を流用しない。
- 論点が「どの会社にも当てはまる一般論」になっていたら絞り込みに失敗している。会社固有性を最も重い物差しにする。
- 対象会社がどの業種の型にも当てはまらない場合、それ自体が最重要の論点である。無理に既存の型に押し込まない。
- **会社の取引区分の呼称をそのまま会計上の分類として扱うと必ず間違える。** 同じ呼称の中に総額・純額の両方が混在していることがある。判定軸で分類し直す。
- 商流の説明が「業界では当たり前」の水準で書かれると、読者は経営者インタビューで質問を作れない。専門用語のまま書かれた箇所は平易化の失敗として差し戻す。
- 会社が合算で開示している売上区分(例:「国内販売」)の中に、会計処理の異なる取引が混ざっていることがある。比率の不自然さ(売上高÷流通総額など)から気付ける。分解を最優先のPBCにする。
- 会計方針の原文を要約して受け取ると論点が消える。原文のまま保存させ、文言と実際の処理・表示の整合を自分で確認する。
